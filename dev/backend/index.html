Backend interface

Everything here is for people adding a backend (a GPU vendor) or a binary ABI (a producer whose kernels take hidden arguments). Users and kernel authors need the API reference only. These names are documented but not public: they will change as backends are added, so pin KernelDispatch's version if you implement them.

The shape of it

A backend is a package extension. It owns a tag (MetalBackendTag, CUDABackendTag, ...), registers itself in LOADED_BACKENDS when its device is usable, and implements the hooks below by dispatching on its tag or its array type. The core never asks "which vendor": it asks the hook.

A binary declares what it is with three facts: its file's format (the extension), its abi (what it takes besides the arguments the caller binds) and its target (the device architecture it was built for). The backend decides what it can launch from those.

Traced CUDA and buffer order. XLA's kernel-call handler hands a launch's buffers over as operands, then results, and binds a kernel's buffer parameters to them in that order. Kernels cannot be asked to list inputs before outputs (KA kernels are f!(out, in...), Triton kernels differ, prebuilt binaries cannot be reordered), so the CUDA embedding passes every output as an extra, zero-filled operand in the kernel's own parameter position and aliases the result to it (output_operand_aliases). The buffers then arrive in the kernel's order, whatever it is, and the repeated result buffers after them go unused. This was measured on an NVIDIA machine (outputs first, last or between scalars); without the aliasing an output-first kernel is bound wrongly and silently. The same mechanism carries an InOutArray: its operand is bound in the kernel's position with the result aliased to it. Metal has no such limit and refuses an InOutArray in a trace.

A backend is complete when it passes test/gpu/conformance.test.jl, which runs the same checks against any loaded backend using an :explicit-ABI kernel.

Launching

KernelDispatch.encode_launch — Function
encode_launch(backend, b::KernelBinary, slots, grid::NTuple{3,Int})

The lowest layer: bind slots (device arrays and bits scalars, in slot order, prelude included) to b's entry point and dispatch it on a 3-D grid of b.threadgroup-thread groups, waiting for completion. Refuses a threadgroup over max_threads. Implemented by the backend extension; callers want run_binary, which builds the slots and grid.

source
KernelDispatch.device_time — Function
device_time(backend, items; reps) -> Float64
device_time(backend, binary::KernelBinary, slots, grid::NTuple{3,Int}; reps) -> Float64

Seconds per repetition of reps repetitions of a sequence of dispatches, all back to back in ONE command buffer (or stream segment), from the device's own timestamps. items are (binary, slots, grid) triples in launch order, slots the bound arguments in slot order as encode_launch takes them; the second form times one dispatch. No warm-up. Implemented by the backend extension (the sequence form); most callers want time_binary, which binds the slots.

source
KernelDispatch.bind_slots — Function
bind_slots(proto, prelude, args, extras) -> (bound, slots)

The one binding rule, shared by every eager launch (execute, time_binary): each OutArray of args is allocated like proto (zero-filled if it asks) and each InOutArray is its array, giving bound; slots are (prelude..., bound..., extras...) in order, a Val taking no slot.

source
KernelDispatch.device_dense — Function
device_dense(backend, x) -> x′

x as an array the backend's launcher can bind directly: a plain, contiguous device array.

A device launcher binds raw buffers, but callers hand it wrappers — a view of a fused projection's output, a reshape. The default is the identity (host arrays, traced arrays, nothing). A backend extension whose launcher needs plain arrays copies a wrapper here, once, on the device.

source
KernelDispatch.LOADED_BACKENDS — Constant
LOADED_BACKENDS

Backends whose extension has loaded AND whose device is usable, as :metal/:cuda/:rocm. Each backend extension adds itself in __init__. use_kernel! consults it so selecting a CUDA kernel on a Metal machine fails at the point of selection rather than at the first launch.

Formats and targets

KernelDispatch.supported_formats — Function
supported_formats(backend) -> Tuple{Vararg{Symbol}}

The binary formats backend launches, as the file extensions binary_format reads: Metal (:metallib,), CUDA (:cubin, :ptx), ROCm (:hsaco,). () (the default, for the host and unknown backends) means unchecked. A fact about the vendor's formats, so it lives here and not in an extension: a traced launch needs it even when only Reactant is loaded.

source
KernelDispatch.binary_format — Function
binary_format(b::KernelBinary) -> Symbol

The format of b.file, from its extension (:cubin for kernel.cubin).

source
KernelDispatch.target_id — Function
target_id(backend) -> String

The architecture of the device backend runs on, as a binary's KernelBinary.target spells it ("sm_86" for CUDA). "" (the default, and Metal) means the device has no architecture that matters: its binaries are portable. Implemented by the backend extension, which can ask the device.

source
KernelDispatch.compatible_target — Function
compatible_target(backend, b::KernelBinary) -> Union{Nothing,String}

nothing when b can run on backend's device, else the reason it cannot (a cubin built for another architecture). The default accepts everything. Implemented by the backend extension.

source
KernelDispatch.check_binary — Function
check_binary(backend, b::KernelBinary)

Refuse, with an explanation, a binary backend cannot launch: a format it does not run, or a target it cannot run on. Cheap and static; done once per prepare_launch, eager or traced. Unchecked for the host.

KernelAbstractions binaries

What a KA binary takes ahead of its arguments is the backend's business: ka_state_words (hidden leading arguments), then ka_prelude (KA's launch context, in whatever form the backend passes it), on a grid ka_grid lays out. Metal passes a state word and the context's bytes. CUDA passes nothing for the state and the context as six integers (the ND-range, then the block counts), because the binary is built by _ka_compile as a flat wrapper entry compiled with CUDA.jl's kernel state switched off, so that XLA's handler can launch it; the wrapper rebuilds the context on the device. The layout is recorded as params.ka_layout (ka_layout), and the CUDA compatible_target refuses a :ka binary without it. The details, and the consequence that a CUDA KA kernel must be free of code that can throw, are on the Backends page.

KernelDispatch.ka_backend_object — Function
ka_backend_object(backend) -> KernelAbstractions.Backend

The KernelAbstractions backend object for backend (MetalBackend() for the Metal tag). Implemented by the backend extension for its own tag. Dispatching on the tag, rather than a hook the extension installs, lets any extension reach it: the Reactant extension hands the tag of the compiling client.

source
KernelDispatch.ka_state_words — Function
ka_state_words(backend) -> Tuple

The bits values a KernelAbstractions-compiled binary takes ahead of KA's launch context, in order: whatever the backend's KA kernels pass as hidden leading arguments (Metal.jl's kernel-state word, say). Implemented by the backend extension for its own tag; () if its kernels take none (CUDA's are built without one). There is no default, so a backend that forgets fails here instead of launching with a shifted argument list.

source
KernelDispatch.ka_context — Function
ka_context(backend, groups::NTuple{3,Int}, tg) -> (ctx, is_ghost)

KA's launch context for a binary dispatched over groups threadgroups of tg threads: the ND-range (groups[1]·tg, groups[2], groups[3]) with workgroup (tg, 1, 1), built on the backend's ka_backend_object. is_ghost: the context occupies no buffer slot.

The context is built from _geometry_probe, an empty KA kernel, not from the kernel the binary was compiled from. A KA context depends only on the launch geometry (ND-range and static workgroup size), never on which kernel it serves, so the probe yields exactly the context the binary was compiled against. That matters because the kernel object is often gone by launch time: a binary loaded from a manifest has no kernel in this session. The context itself comes from KA's own launch_config and mkcontext, never built by hand, so its layout stays KA's business.

source
KernelDispatch.ka_grid — Function
ka_grid(backend, groups::NTuple{3,Int}) -> NTuple{3,Int}

The 3-D grid of threadgroups a KernelAbstractions binary is dispatched on, given the groups it covers (the ones its ka_context was built from). Implemented by the backend extension: how a backend lays out threadgroup positions is its own business (Metal's KA kernels read only the x component, so it flattens). No default, so a backend that forgets fails here instead of launching a grid its kernels misread.

source
KernelDispatch.ka_prelude — Function
ka_prelude(backend, ctx, ghost) -> Vector{Any}

What a KernelAbstractions-compiled binary takes ahead of its arguments: the backend's ka_state_words, then KA's launch context unless it is a ghost type. (A backend may pass the context in another form: CUDA passes its six integers, the ND-range and the block counts, as separate scalars.) A Vector{Any}: the context's type depends on the threadgroup VALUE, and keeping that out of the binder's signature keeps call_binary inferable.

source
KernelDispatch.ka_layout — Function
ka_layout(backend) -> Union{Nothing,Symbol}

How backend lays out what a KernelAbstractions binary takes ahead of its arguments, when that is a layout it has changed over time: nothing (the default, and Metal) records nothing. A backend that returns a symbol has ka_compile store it in the binary's params as ka_layout, and can refuse (through compatible_target) a binary built with another layout instead of launching it with shifted arguments. CUDA returns :flat: no kernel-state argument, and KA's context as six plain integers.

source

ABIs

KernelDispatch.abi_prelude_and_grid — Function
abi_prelude_and_grid(::Val{abi}, backend, b::KernelBinary, groups) -> (prelude::Vector{Any}, grid::NTuple{3,Int})

What a binary of a non-built-in ABI (b.abi, neither :explicit nor :ka) takes ahead of its arguments, and the grid it is dispatched on. An extension that supports such a binary (a Triton one, say) defines a method for its Val{:name}. No default: a binary whose ABI nothing implements is refused here, not launched with a shifted argument list.

source

Reactant traces

KernelDispatch.custom_call — Function
custom_call(backend, entry, path, operands, result_shapes, layout; grid, threadgroup, result_eltypes)
    -> results

Embed the kernel entry of the compiled binary at path in a traced program as a stablehlo.custom_call, in the form backend's XLA client understands. layout is the kernel's argument table in order, as (:in, i), (:out, i), (:out_zero, i) or (:bytes, payload).

Which binaries a backend's custom call can carry is handled by traced_support.

A generic, so each backend extension adds a method for its own tag (the Reactant extension provides Metal's, for jax-mps, and CUDA's, for XLA's triton_kernel_call handler, which launches binaries that take only pointers and scalars). The traced execute calls it with the tag of the compiling client.

source
KernelDispatch.traced_support — Function
traced_support(backend, b::KernelBinary) -> Union{Nothing,String}

nothing when b can be launched from a Reactant trace on backend, else why not. Asked at the top of the traced execute, before any argument is converted, so the reason reaches the user instead of whatever the unsupported binary would have tripped over first. The default accepts everything, and so does every backend today: CUDA's KA binaries are built flat (pointers and scalars only), which XLA's kernel-call handler can pass. A backend whose custom call cannot carry some binary (struct arguments, say) overrides this to say why.

Adding a backend

The checklist, in the order that finds problems fastest. ROCm is the next vendor, and the notes say what is likely to differ.

  1. A tag and its formats. MetalBackendTag, CUDABackendTag and ROCmBackendTag already exist in src/backend.jl with their supported_formats (.hsaco for ROCm). A new vendor adds a tag and a method.
  2. An extension that loads on the vendor's package, pushes the tag onto LOADED_BACKENDS in __init__ only when the device is usable, and defines backend_of for its arrays and device_dense for the wrappers (views, adjoints) that are not plain device arrays.
  3. Launching. execute(::MyArray, ::Launch) using bind_slots, encode_launch, device_time and max_threads. The conformance suite exercises exactly these.
  4. Architecture. target_id and compatible_target. CUDA accepts a cubin from the same major version when the device's minor is at least its own; for ROCm expect an exact gfx match (with a few family rules), not CUDA's rule.
  5. KernelAbstractions binaries. ka_backend_object, ka_state_words, ka_prelude, ka_grid, optionally ka_layout, and _ka_compile. What the vendor's KA kernels take as hidden leading arguments must be read from the vendor's package, not assumed from CUDA or Metal.
  6. Traced launches. custom_call and traced_support. First find out how the XLA client behind Reactant launches a kernel image at all (which custom-call target and API version it accepts; CUDA's is selectable with KERNELDISPATCH_CUDA_CUSTOM_CALL, so a candidate can be tried per process). Until something works, make traced_support say so and leave custom_call unimplemented, so a traced launch fails with an explanation. Whether the vendor's handler binds buffers in a fixed order, and whether aliased outputs lift that, is measured with a kernel that writes a different value to each buffer, run in every order.
  7. Tests. Add test/ext/<backend>/backend.jl, the adapter the generic tests in test/gpu/ run through, and a candidate in test/gpu_backend.jl. The adapter defines the device array type, the backend's thread limit, its array-wrapper union, an :explicit-ABI scale fixture (hand-written PTX for CUDA, a committed .metallib for Metal), a binary in a format it must refuse, its traced Reactant client and the custom call's name, the KA state words it expects, and any prebuilt SDPA kernels (the full list is in test/gpu_backend.jl). The backend is complete when the generic tests pass, test/gpu/conformance.test.jl first. Tests for what only this backend does go beside the adapter, and for a machine you can only reach remotely a staged script in the style of test/ext/cuda/smoke.jl.

For ROCm specifically: the code object is a .hsaco; wavefronts are usually 64 wide (so threadgroup multiples and a Triton threadgroup of num_warps * warp_size differ from CUDA's 32); and triton_binary keeps NVIDIA-only logic (sm_*, .cubin/.ptx, the CUDA scratch-pointer convention) that would move behind a per-vendor hook.
