API reference

This page is the API: what a user calls and what a kernel author defines. What a backend implements (a new GPU vendor, a new binary ABI) is on the backend interface page and may change.

KernelDispatch.KernelDispatch — Module
KernelDispatch

Run operations as compiled kernels: eagerly on device arrays, embedded as custom calls in a Reactant-compiled program, or as plain Julia on cpu. Kernels are switchable per op and tuned variants picked from the inputs. See the documentation for tutorials and the API reference.

Ops and kernels

KernelDispatch.AbstractKernelOp — Type
AbstractKernelOp

An operation that runs as compiled kernels. Subtype it with a singleton:

struct Axpy <: AbstractKernelOp end

Its name (opname) defaults to the type's; define it for an identifier that survives renaming.

Calling it (Axpy()(args...)) runs host on host arrays and forward on device arrays, with its default_kernel or the one selected by use_kernel!.

source
KernelDispatch.AbstractKernel — Type
AbstractKernel

One implementation of an op, switchable with use_kernel!:

struct AxpyKA <: AbstractKernel end

Its name (kernelname) defaults to the type's; define it for an identifier that survives renaming. Nothing needs registering: an op's @default_kernel candidates and any kernel passed to use_kernel! are registered on first use.

It needs a forward method (and a backward one to differentiate), which build its binary's arguments and launch it with call_binary. Its other methods (variant_key, extras, nearest, build!, source_tag) say how its binaries are chosen and launched.

source
KernelDispatch.KernelBinary — Type
KernelBinary(file; entry=basename without extension, threadgroup, tile=(threadgroup, 1, 1),
    params=(;), abi=:explicit, target="")

One compiled launch, everything about it persisted with it in the manifest.

  • file is the compiled binary: a .metallib on Metal; a .cubin or .ptx on CUDA (a cubin is machine code for one architecture, PTX is text the driver or XLA compiles at load). Any other extension is refused on CUDA.

  • entry is the name of the kernel function inside file, the one the runtime launches. It defaults to the file name without its extension, which is right whenever the file is named after its function (trifast's _fwd.metallib, everything from ka_compile). Set it only when the function is named otherwise, or the file holds several functions. It is fixed here, from the original path, because add_variant! copies the file into the registry under a new name. It is unrelated to the launch name a variant files the binary under (fwd= in add_variant!, the name call_binary takes): that is your label for its role, this is the toolchain's name for it.

  • threadgroup is the number of threads per threadgroup the binary is dispatched with.

  • tile is how much of the problem one threadgroup covers along each axis: call_binary launches cld.(extent, tile) threadgroups for the extent a call passes it. The default, (threadgroup, 1, 1), is one item per thread; a Triton kernel running one program per item has tile=(1, 1, 1), a kernel tiling a matrix in 32×32 blocks (32, 32, 1). An integer or a shorter tuple is padded with 1s. It is a property of the build, so it changes with the binary when retuned. Any grid can be launched this way: with tile=1, the extent IS the grid.

  • params are the tuning numbers it was built with, for extras to read.

  • abi says what the binary takes besides the arguments call_binary binds, so the launcher can supply it. :explicit (the default) takes nothing: exactly the buffers and scalars you bind, in the order given, with nothing added or implied (:plain, its earlier name, is still accepted). :ka marks a binary compiled from a KernelAbstractions kernel (ka_compile sets it): it takes the backend's ka_state_words and KA's launch context ahead of its arguments (in the form the backend's ka_prelude gives; CUDA passes the context as six integers), and is dispatched flat. An extension can define another ABI (see abi_prelude_and_grid). It is a property of the binary, not of the kernel type that holds it: one kernel can register a KA-compiled binary for one launch and a Triton one for another. (is_ka=true and b.is_ka remain as deprecated aliases for abi=:ka.)

  • target names the device architecture the binary was built for ("sm_86" for a CUDA cubin), "" when it is portable (a .metallib, PTX). ka_compile sets it; a prebuilt file can say it, so a launch on a device it cannot run on is refused with an explanation instead of failing in the driver.

  • shared_mem is the dynamic shared memory, in bytes, each threadgroup is launched with (a Triton kernel's shared; see triton_binary). 0 for a kernel that declares its threadgroup memory itself, as every Metal and KernelAbstractions kernel does. Metal ignores it.

KernelDispatch.OutArray — Type
OutArray(T, dims...; zero=false)

An output argument: a fresh T array of size dims, allocated eagerly or declared as a result in a trace, in the argument's place. zero = true zero-fills it first, for a kernel that accumulates.

source
KernelDispatch.InOutArray — Type
InOutArray(x::AbstractArray)

An argument the kernel both reads and updates in place (y += a * x, a read-modify-write output), bound where the array would be. It is returned among the outputs, in OutArray order, as the UPDATED array:

  • eagerly it is x itself, written by the kernel (so x must be a dense device array, not a view or wrapper that would have to be copied: that is refused);
  • in a trace the array is the call's operand and its result is aliased to it (output_operand_aliases), so the kernel sees x's values, and the returned array is the updated one. XLA copies x first if it is still used afterwards, so the program stays functional: x itself is not changed.

An OutArray starts as a fresh (zero) buffer, an InOutArray starts as x. Not supported on Metal under a trace (jax-mps cannot alias a result to an operand).

KernelDispatch.opname — Function

opname(op) -> Symbol: the op's name, its identifier outside the running code: the REPL shorthand (use_kernel!(:Axpy, …)), its preference key ("kernel.<opname>") and its registry directory. Default: the op type's name. Define it to keep those stable when the type is renamed.

source
KernelDispatch.kernelname — Function

kernelname(kernel) -> Symbol: the kernel's name within its op, its identifier outside the running code: the REPL shorthand, the value a default-kernel preference holds, its registry directory. Default: the kernel type's name. Define it to keep those stable when the type is renamed.

source
KernelDispatch.host — Function
host(op, args...)

The op on host arrays. Runs whatever kernel is selected: the selection applies on a device.

source
KernelDispatch.forward — Function
forward(op, args...)
forward(op, kernel, args...)

The op on device arrays. The first form runs the selected kernel. The second is defined per op and kernel, and is required: it builds the binary's arguments from the op's (outputs as OutArray, sizes and scalars in the binary's types), launches it with call_binary (extent= the problem size), and returns what the op's callers should get.

There is no working default: a binary's calling convention can't be guessed, and passing the op's arguments through unchanged would bind them wrongly, silently. A kernel without a forward throws.

source
KernelDispatch.backward — Function
backward(op, kernel, args, outs, cotangents) -> Tuple

Gradients of forward(op, kernel, args...), one per argument (nothing for one with none), given its outputs outs and their cotangents. No default: overload it to make an op differentiable.

source

variant_key(op, kernel, args...) -> Tuple: which tuned variant serves these arguments. Default ().

extras(op, kernel, binary) -> Tuple: arguments appended to the caller's (tuning values). Default ().

nearest(op, kernel, keys, key): a registered key to use when key has no exact variant, or nothing.

build!(op, kernel, key): create the variant for key (a lazy tune) via add_variant!. Default: nothing.

source

source_tag(kernel) -> String: a manifest recorded with another tag is ignored. Default "".

cache_dir(op) -> String: where the op's kernels keep their manifests and binaries. Default: ops/<Package>.<opname> under cache_root, so equally named ops from different packages (or a script, Main) never share a registry.

Selecting a kernel

KernelDispatch.@default_kernel — Macro
@default_kernel Op kernel₁ kernel₂ ...

Give op type Op its default kernel: the one its package's preference "kernel.<opname>" names (set with set_default_kernel!), else kernel₁. The kernels listed are the candidates; their kernelnames are what the preference holds.

Use it at the top level of the package declaring Op, after the kernels' kernelname methods:

KernelDispatch.@default_kernel Softmax OnlineSoftmax() TwoPassSoftmax()

Outside a package (a script, Main) there are no preferences, and the default is kernel₁.

source
KernelDispatch.default_kernel — Function
default_kernel(op) -> kernel or nothing

The kernel op runs unless use_kernel! overrides it. Defined by @default_kernel in the op's package; nothing (no default) otherwise.

source
KernelDispatch.default_candidates — Function

default_candidates(op) -> Tuple: the kernels @default_kernel lists for op. Default ().

source
KernelDispatch.use_kernel! — Function
use_kernel!(op, kernel_name) -> Symbol
use_kernel!(op, kernel) -> Symbol

Select which kernel op runs for the rest of the session, overriding its default_kernel. op is the op (Axpy()), its type (Axpy) or its name (:axpy); the kernel is the kernel itself (AxpyPlain()), registered on the way if it is new to the op, or its name (:plain), for a kernel already registered or listed in the op's @default_kernel. Not persisted: see set_default_kernel!.

Selection is the application's decision: global per op, it affects every caller in the session, so a library never switches. A library that needs one particular kernel calls forward(op, kernel, args...).

The selection is a method, so op calls stay inferred; code calling the op recompiles on its next call. It takes effect from the NEXT top-level expression (REPL input, script statement): later in the same function or begin/let block the op call throws, rather than run the previous kernel. (A @testset body sees it at once.) To run one call with a particular kernel, call forward(op, kernel, args...) instead: no switch, no recompilation.

source
KernelDispatch.reset_kernel! — Function

reset_kernel!(op): drop the use_kernel! override; op runs its default again.

source
KernelDispatch.current_kernel — Function

current_kernel(op) -> Symbol or nothing: the kernel op runs (as of the newest world).

source
KernelDispatch.selected_kernel — Function
selected_kernel(op) -> kernel

The kernel op runs now: the use_kernel! override, else its default_kernel. Unlike current_kernel, which returns the NAME as of the newest world, this returns the kernel itself and is inferred, so it is what to call (and dispatch on) from code that runs the op. Throws when none is selected, and on a call from code compiled before the latest switch (see use_kernel!).

source
KernelDispatch.list_kernels — Function

list_kernels(op): every kernel of op (registered, or one of its @default_kernel candidates), its variant count, and which is selected.

source
KernelDispatch.set_default_kernel! — Function
set_default_kernel!(op, kernel_name)

Persist kernel_name as op's default: a compile-time preference of the package declaring op, written to the active project's LocalPreferences.toml. It takes effect in the next session (the package and its dependents re-precompile once, with the kernel baked in); use_kernel! switches the current one. kernel_name must be one of the op's @default_kernel candidates.

source
KernelDispatch.clear_default_kernel! — Function

clear_default_kernel!(op): remove the preference set_default_kernel! wrote.

Registering variants

KernelDispatch.register_kernel! — Function
register_kernel!(op, kernel) -> kernel

Make kernel known to op by name, and op by its name: for use_kernel!(op, name) and list_kernels. (Re)loads the kernel's persisted variants.

Rarely needed: an op's @default_kernel candidates are registered on first use, and use_kernel!(op, kernel) registers the kernel it selects. Call it to have another kernel (say, one from another package) selectable by name and listed before its first use. Registering the same kernel again only reloads its manifest; a DIFFERENT kernel under a name the op already has throws, as does a different op under a name already taken: they would share one entry, directory and manifest.

source
KernelDispatch.add_variant! — Function
add_variant!(op, kernel, key; binaries...) -> Variant

Register the variant for key: one KernelBinary per launch name (fwd=…, dq=…). Each binary is COPIED into the kernel's cache directory (so it survives its original moving) and the manifest is rewritten. The copy is named <launch name>_<id>.<ext>, id being the first 8 hex digits of a hash of the file's contents, key and the launch name: a different binary never takes a registered one's file. Binaries no variant names any more are removed.

source
KernelDispatch.variants — Function

variants(op, kernel; target=current_target()) -> Dict{Tuple,Variant}: the kernel's variants, by key, for the device architecture target (see current_target): binaries built for one architecture are kept apart from another's. The first access in a session loads them from the kernel's manifest, so persisted variants need no registration.

source
KernelDispatch.variant — Function
variant(op, kernel, key; target=current_target()) -> Variant

The variant serving key: an exact match, else the kernel's nearest choice, else what its build! creates. Throws when none exists. target selects the architecture's variants; build! always builds for the current device, so a lookup for another target only finds what is registered.

Launching binaries

KernelDispatch.call_binary — Function
call_binary(op, kernel, name, args...; key=variant_key(op, kernel, args...), extent) -> Tuple

Launch binary name of the variant for key, binding (args..., extras(op, kernel, binary)...) IN THE ORDER GIVEN: an OutArray is allocated (or a traced result), an array is bound in place, an InOutArray is an array the kernel updates (returned too), a number by value, a Val not at all. Returns the outputs, in the order of the OutArrays and InOutArrays. Getting the order right is the caller's job.

It launches cld.(extent, tile) threadgroups: the problem size extent (an integer or a tuple of up to three axes, required) divided by what one threadgroup of the binary covers, its tile.

The op-level layer: it finds the binary and its extras, then run_binary does the rest. The outputs are picked from args alone: extras (which may read KernelBinary.params, typed only at run time) are only bound, so whatever they return never reaches the result's type. They must therefore not contain OutArrays.

source
KernelDispatch.run_binary — Function
run_binary(b::KernelBinary, args...; extent, extras=(), label=Symbol(b.entry)) -> Tuple

Launch b on args and return the outputs: execute(prepare_launch(b, args...; …)). The binary-level layer under call_binary, which adds the registry lookup; call it directly to run a binary that is not registered (a tuner's candidate). Eager or traced, like call_binary.

source
KernelDispatch.prepare_launch — Function
prepare_launch(b::KernelBinary, args...; extent, extras=(), label=Symbol(b.entry)) -> Launch

Turn a problem size into a concrete Launch of b, without running it: cld.(extent, b.tile) threadgroups, the prelude and grid of the binary's ABI (KA's context and flat grid for :ka), device wrappers densified (device_dense). The binary need not be registered. Binding follows call_binary: (args..., extras...) in the order given.

source
KernelDispatch.Launch — Type
Launch

One concrete launch of a KernelBinary, made by prepare_launch and run by execute or timed by time_binary:

  • binary: what is launched;
  • args, extras: the arguments as they will be bound (device wrappers already densified), OutArrays still unallocated. args is a typed tuple, so the outputs' types infer;
  • prelude: what the binary takes ahead of its arguments (for an abi = :ka binary the backend's state words and KA's context, else nothing);
  • groups: the threadgroups the problem needs, cld.(extent, tile);
  • grid: the grid actually dispatched (groups, flattened by ka_grid for an abi = :ka binary);
  • label: its name in record_bindings.
source
KernelDispatch.execute — Function
execute(l::Launch) -> Tuple

Run a prepared Launch and return its outputs, in OutArray order. What running means is the arrays' business: eager device arrays are launched (the backend extension's execute(proto, l) method), traced arrays become a custom call, and inside record_bindings nothing runs.

source
KernelDispatch.time_binary — Function
time_binary(l::Launch; reps=3, warmup=1) -> Float64
time_binary(ls::AbstractVector{<:Launch}; reps=3, warmup=1) -> Float64
time_binary(b::KernelBinary, args...; extent, extras=(), reps=3, warmup=1)
time_binary(op, kernel, name, args...; key=variant_key(op, kernel, args...), extent, reps=3, warmup=1)

Seconds per dispatch of a binary on the device: warmup untimed launches, then ONE device_time of reps dispatches back to back, from the device's own timestamps. Host-side launch latency is excluded. Repeating the call and taking a minimum is the caller's policy.

The core form times a prepared Launch. A vector of launches is timed as a sequence: each repetition dispatches all of them in order, in the same command buffer, and the result is seconds per repetition — a whole forward or backward of several binaries (record_bindings hands over the launches an op call makes). The third form prepares a launch for a binary that need not be registered (a tuner's candidate); the fourth resolves the registered variant and its extras as call_binary does. All bind with bind_slots, exactly as an eager execute.

OutArrays are allocated once and reused by every dispatch (a zero=true one is zeroed once only), so their contents afterwards are meaningless and are not returned. The reps dispatches share cache state, which flatters a bandwidth-bound kernel slightly against a cold call.

Throws if a binary's threadgroup exceeds max_threads, on host arrays, for launches on different backends, and while tracing (timing is eager device work, which the tracer would capture).

source
KernelDispatch.record_bindings — Function
record_bindings(f) -> Vector{(; label, slots, groups, launch)}

Run f() with every eager launch replaced by a record of what it would bind: the launch's label (the name call_binary was given), its slots in order, each kind => value with kind one of :bytes (the KA prelude), :out (an allocated output), :inout (an array updated in place), :in (an array), :scalar, and the threadgroups it would launch, groups (cld.(extent, tile), before any flattening by ka_grid), and the Launch itself, which can be run or timed later (execute, time_binary) to replay what f launches. Nothing is dispatched. A record destructures as label, slots, groups = rec.

source
KernelDispatch.max_threads — Function
max_threads(binary::KernelBinary; backend=device_backend()) -> Int
max_threads(backend, binary::KernelBinary) -> Int

The compiled binary's own threads-per-threadgroup ceiling: what its register use leaves of the device's. Dispatching over it does not raise but returns garbage AND an impossibly fast time, so eager launches and time_binary refuse it; a tuner asks this first to skip the candidate. The two-argument form is implemented by the backend extension.

KernelAbstractions kernels

KernelDispatch.ka_compile — Function
ka_compile(backend, kernel, argtypes::Tuple; tg, name, params=(;), tile=(tg, 1, 1), dir=ka_binary_cache_dir(target_id(backend))) -> KernelBinary

Ahead-of-time compile the KernelAbstractions kernel at workgroup size tg to a binary at joinpath(dir, name * ext) whose entry point is name, and return it as a KernelBinary with abi = :ka (and the given tuning params), ready for add_variant!. Rebuilt only when absent — put a source hash in name. tile defaults to one item per thread; a kernel whose threads each cover several items says so here.

This is the KernelAbstractions producer of binaries and it belongs to the launch side: the binary is built against the launch context (ka_context) and argument pointer types that call_binary binds for an abi = :ka binary, so compiling by other means binds wrongly, silently. dir is where the file is built, by default ka_binary_cache_dir: not part of the registry, which is where kernels live. add_variant! copies what it registers into it.

On CUDA the binary is built without CUDA.jl's kernel state (and with KA's context as six plain integers): its parameters are only device pointers and scalars, so the same file launches eagerly and from a Reactant trace. The price is that a kernel whose compiled code can still throw (a bounds check, a DomainError, error) is refused here, at build time, because a device cannot report an exception without that state; index with unsafe_load / unsafe_store! as the binary contract already says. params gains a reserved ka_layout entry (ka_layout).

argtypes lists the kernel's arguments after KA's context, in signature order: AbstractArray{T} for a buffer (bound as a raw device pointer to T; the kernel indexes it with unsafe_load / unsafe_store!), a bits type for a scalar, Val{x} for a compile-time parameter — the order call_binary will bind them in.

source
KernelDispatch.ka_binary_cache_dir — Function
ka_binary_cache_dir(target=current_target()) -> String

Where ka_compile builds binaries by default: ka under cache_root, in a subdirectory named for the device architecture (ka/sm_86) when there is one, so a cache shared by machines with different GPUs never serves one's binary to another. Output is only staged here — add_variant! copies a registered binary into the registry, which is where kernels live — but it is kept between sessions, so a name already built is found, not rebuilt.

source

Triton kernels

KernelDispatch.triton_binary — Function
triton_binary(metadata_json; image=nothing, tile=1, params=(;), scratch_pointers=nothing) -> KernelBinary

Describe a kernel Triton compiled for NVIDIA as a KernelBinary (abi = :triton), from the metadata JSON Triton wrote beside its output (<name>.json next to <name>.cubin and <name>.ptx). Where those files are is your build step's choice: compile ahead into a directory you control. (Triton's own JIT cache, <hash>/ directories under its cache directory, TRITON_CACHE_DIR to move it, also holds them, but the hash names are opaque and Triton may rewrite or clear them.) Register it like any binary:

add_variant!(op, kernel, key; fwd=triton_binary("scale_kernel.json"))
  • image: the .cubin or .ptx to launch. Default: the .cubin beside the JSON, else the .ptx. A cubin is machine code for the architecture the metadata names (recorded as the binary's target); PTX is portable.
  • tile: how much of the problem one Triton program covers (see KernelBinary). The default 1 makes extent the grid of programs, which is how Triton is launched.
  • scratch_pointers: how many hidden trailing pointer parameters the compiled kernel takes after its own. Read from the metadata: one for each of the global_scratch_size and profile_scratch_size entries it has (both are present in Triton 3.8.0, whose kernels end in exactly two pointers). Pass it to override for another version.

The kernel's entry, threadgroup (num_warps times the target's warp size) and shared_mem come from the metadata, which must have the keys Triton 3.8.0 writes (name, num_warps, target with backend, arch and warp_size). What cannot be launched is refused here, with an explanation: a non-NVIDIA target, num_ctas above 1 (thread-block clusters), and a kernel that needs global scratch memory (global_scratch_size > 0).

The arguments call_binary binds must be exactly the ones the compiled kernel declares: Triton drops constexpr arguments from the signature, and (depending on its version) integers it specialized to 1. The order of the buffers is the kernel's own: a Reactant trace passes each output as an aliased operand in its position.

KernelBackend

Where a kernel call will execute. Not the array type: a TracedRArray is the same Julia type whether it will run on CPU or GPU, and the distinction only exists in the XLA client.

backend_of(x) -> KernelBackend

The backend an array will execute on.

Autodiff and tracing

KernelDispatch.tracing — Function
tracing() -> Bool

Whether we are inside a Reactant trace. false without the Reactant extension.

Building a kernel on demand (a lazy tune, say) runs eager device work, which the tracer would capture into the graph; owners check this and refuse instead.

source
KernelDispatch.traced_autodiff — Function
traced_autodiff(x) -> Bool

Whether x is being traced inside an Enzyme.autodiff/gradient call under Reactant. false by default; the Reactant extension answers for traced arrays (Reactant.WITHIN_AUTODIFF).

Enzyme-JAX cannot yet differentiate a stablehlo.custom_call through an attached reverse rule (EnzymeAD/Enzyme#2516), so a kernel call traced inside autodiff THROWS rather than quietly running something else in both directions. See KERNEL_IN_TRACED_AUTODIFF.

source
KernelDispatch.KERNEL_IN_TRACED_AUTODIFF — Constant
KERNEL_IN_TRACED_AUTODIFF

Ref{Bool}, default false. With false, a kernel call traced inside Reactant autodiff throws (see traced_autodiff). Set it to true once the Enzyme-JAX in use can differentiate a custom call through its attached reverse rule.
